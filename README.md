# Подготовка Ubuntu-сервера для Laravel

## Быстрый старт на чистом сервере

После входа **под root** скопируйте весь блок. Для публичного репозитория
используется HTTPS: SSH-ключ GitHub для скачивания скриптов не нужен.

```bash
apt-get update -o APT::Update::Error-Mode=any &&
apt-get install -y git ca-certificates &&
git clone https://github.com/alexmihel/server-script.git /root/server-script &&
cd /root/server-script &&
bash setup.sh
```

Скрипт сам создаст `.env` и запросит настройки. `chmod +x` не требуется.
Команды связаны через `&&`: при ошибке следующий шаг не запустится.
Для повторного запуска уже скачанных скриптов:

```bash
cd /root/server-script && bash setup.sh
```

Ошибка `Package 'git' has no installation candidate` на чистом сервере часто
означает, что ещё не загружены индексы пакетов — поэтому первым идёт `apt-get update`.
Если обновление завершилось с ошибкой или Git всё ещё недоступен, нужно проверить
APT-источники, доступ к зеркалу/DNS и поддержку версии Ubuntu; повторная команда
`apt install git` это не исправит.

## Конфигурация перед запуском

Скрипты запускаются через `sudo bash`, из любого каталога. Один конфиг объединяет
все шаги: пользователь, проект, PHP, Git-провайдер, домен и параметры БД.
Это **конфиг установки сервера**, не Laravel `.env`.

```bash
cp .env.example .env
chmod 600 .env
nano .env
sudo bash setup.sh
```

Можно заполнить файл на компьютере и передать на сервер через `scp`. Не кладите
его в `public/`. После запуска конфиг имеет владельца root и права `600`; для
правок используйте `sudoedit .env`. Отсутствующие значения запрашиваются один раз,
ответы сохраняются. Чтобы изменить сохранённое значение, отредактируйте файл.
Формат: `KEY=value`, допускаются внешние одинарные/двойные кавычки, строки
комментариев начинаются с `#`. Нет выполнения shell-кода, подстановок переменных,
`export` и комментариев в конце значения. Неизвестные ключи считаются ошибкой.
Пароль PostgreSQL в конфиг не записывается.

Для нескольких проектов используйте разные конфиги и, желательно, пользователей:

```bash
sudo bash setup.sh --config /root/site-a.env
sudo bash setup_git.sh --config /root/site-a.env
```

Не запускайте два процесса настройки с одним конфигом одновременно.

## Последовательность

1. `server_setup.sh` — проверка пакетов PHP и разрешимости зависимостей; установка
   Nginx, выбранного PHP-FPM, PostgreSQL, Redis, Supervisor, Git, Certbot, Fail2ban,
   unattended-upgrades и Composer 2; создание пользователя; настройка UFW.
2. `setup_git.sh` — выбор `github`/`bitbucket`, создание Ed25519-ключа от имени
   пользователя сайта, вывод публичного ключа и ссылки для регистрации. После
   регистрации проверяет чтение выбранного репозитория через `git ls-remote`.
3. `create_postgres_db.sh` — создание базы/роли на выбранном **существующем** порту
   кластера. Повторный запуск обновляет пароль роли и проверяет владельца базы.
   Порт PostgreSQL не перенастраивается. Для другого кластера укажите его порт.
4. `setup_laravel_project.sh` — клонирование в `/var/www/PROJECT_NAME` и ACL.
   Существующий репозиторий с тем же origin получает исправление прав; рабочая
   копия не обновляется и не очищается. Чужой/обычный непустой каталог отклоняется.
5. `create_nginx_domain_with_ssl.sh` — конфиг Nginx, проверка `nginx -t`, HTTPS и
   таймер продления Certbot. `INCLUDE_WWW=true` добавляет сертификат для www.
   DNS **всех** выбранных имён должен указывать на сервер; порты 80/443 доступны.
   Первый запуск Certbot принимает условия Let's Encrypt.

Шаги можно запускать отдельно. `setup.sh` спрашивает, какие из них выполнить,
останавливается при ошибке и не удаляет Apache автоматически.
`install_phpredis.sh` оставлен для отдельной установки/восстановления Redis:
используется пакет `phpX.Y-redis`, без PECL и компиляции под случайную версию PHP.
`remove_apache.sh` требует явного подтверждения и удаляет только пакеты,
сохраняя содержимое сайтов и журналы. Если Apache занимает 80/443, сначала
разберитесь с ним, затем устанавливайте Nginx.

`NON_INTERACTIVE=true` позволяет запускать отдельные шаги с заполненным конфигом.
Недостающие обязательные значения приводят к ошибке. Настройка Git в этом режиме
только готовит ключ; регистрацию и первоначальную проверку хоста нужно сделать
отдельно. Создание БД и удаление Apache требуют интерактивного ввода.

## Пользователь, Git и права

Пользователь сайта создаётся без пароля и без sudo. Существующий административный
SSH-вход сохраняется: скрипты не редактируют `sshd_config`, не отключают root/пароли
и не копируют ключи администратора. UFW не сбрасывается; разрешаются обнаруженные
порты SSH и `SSH_PORT`. При нестандартной socket activation/NAT предварительно
укажите фактический порт в конфиге. Для прямого SSH-входа пользователя сайта
настройте его `authorized_keys` отдельно. Работать через администратора можно так:

```bash
sudo -iu deploy
cd /var/www/my_project
git pull
php8.3 /usr/local/bin/composer install --no-dev --optimize-autoloader
php8.3 artisan about
```

Git-ключи: `~/.ssh/id_ed25519_github` или `~/.ssh/id_ed25519_bitbucket`; существующий
ключ сохраняется. Ключ без passphrase предназначен для серверного развёртывания.
Для одного проекта предпочтителен Deploy/Repository Access key с правом чтения.
Поддерживаются SSH URL вида `git@github.com:owner/repository.git` и аналогичный
Bitbucket Cloud URL. Self-hosted Git, HTTPS-токены и несколько ключей одного
провайдера для одного пользователя в этом сценарии не поддерживаются.
Проверка ключа хоста SSH остаётся включённой: при первом соединении сверьте
отпечаток с документацией провайдера перед подтверждением.

Владелец репозитория — пользователь сайта и его реальная primary group.
Исполняемые биты файлов сохраняются. `www-data` получает чтение кода, без записи
и без доступа к `.git`; запись разрешена в `storage` и `bootstrap/cache`.
Default ACL обеспечивают доступ к новым файлам, созданным CLI и PHP-FPM.
Если Laravel `.env` загружен с правами `600`, выдайте чтение явно:
`sudo setfacl -m u:www-data:r-- /var/www/my_project/.env`. Владельцем файла
должен оставаться пользователь сайта.
Используется стандартный Ubuntu FPM pool `www` с пользователем `www-data`;
изоляция нескольких приложений отдельными FPM-пулами в эти скрипты не входит.

`INSTALL_COMPOSER_DEPS=true` включает `composer check-platform-reqs --lock`,
`composer install --no-dev` и повторную проверку требований выбранным PHP,
всё от пользователя сайта. Требуется `composer.lock`. Composer scripts выполняют
код проекта: сначала подготовьте Laravel `.env`, если приложению он необходим.
Вручную остаются APP_KEY, секреты приложения, миграции, сборка frontend, cron
и конфигурация queue workers. Скрипт не объявляет приложение готовым до этих шагов.

## Совместимость и обновления

По умолчанию `PHP_VERSION=8.3`. `PHP_SOURCE=auto` сначала проверяет все необходимые
пакеты в подключённых APT-источниках. Если их нет, проверяет наличие Release-файла
PPA Ondřej **для текущего codename**, добавляет PPA и повторяет проверку.
`ubuntu` запрещает автоматическое добавление PPA (уже подключённые источники
сохраняются); `ondrej` явно запрашивает попытку подключения PPA.
Недоступную версию нельзя незаметно заменить: выводятся версии FPM из APT,
запрашивается выбор; в автоматическом режиме — ошибка.
Перед установкой выполняется `apt-get --simulate install`.

Аудит на 29.09.2026:

- Ubuntu 22.04/24.04/26.04 — текущие LTS. Старые EOL/ESM-выпуски не являются целью
  этих скриптов; наличие пакета само по себе не доказывает поддержку безопасности.
- PHP 8.3 получает только security fixes до **31.12.2027**. PHP 8.2 — до
  **31.12.2026**. Для новых приложений выбор 8.4/8.5 зависит от `composer.lock`.
- В каталоге PPA на дату проверки есть `jammy`/`noble`, но нет `resolute`.
  Поэтому 8.3 на Ubuntu 26.04 нельзя обещать. Скрипт проверяет реальное состояние
  источников при каждом запуске; появление поддержки не требует изменения кода.
- Nginx, PostgreSQL, Redis, Supervisor, Certbot и Fail2ban берутся из репозиториев
  текущей Ubuntu; фиксация старых upstream-версий убрана/не добавляется. Ubuntu
  может переносить security fixes без изменения основной версии пакета.
- Composer 2 скачивается с проверкой SHA-384 установщика. Глобальный CLI `php`
  не переключается: используйте `phpX.Y` также в cron/Supervisor.
- Старый `apache2.2-common`, PECL-сборка Redis и заголовок X-XSS-Protection удалены.
  Fail2ban использует journald; общий `apt upgrade` и сброс UFW исключены.
- Включён unattended-upgrades со стандартной политикой Ubuntu. Обновления
  стороннего PPA и Composer нужно контролировать отдельно; автоматические
  security updates для всех Universe/PPA-пакетов не гарантируются.

Проверка фактических installed/candidate-версий и зависимостей без установки ПО:

```bash
sudo bash check_compatibility.sh --config /root/site-a.env
```

Она обновляет APT-индексы и конфиг, но не добавляет PPA. Для точного отчёта нужна
целевая машина: важны версия Ubuntu, архитектура, источники и pinning APT.

Источники:
[Ubuntu releases](https://ubuntu.com/project/docs/release-team/list-of-releases/),
[PHP lifecycle](https://www.php.net/supported-versions.php),
[PPA distributions](https://ppa.launchpadcontent.net/ondrej/php/ubuntu/dists/),
[Composer installer verification](https://getcomposer.org/doc/faqs/how-to-install-composer-programmatically.md),
[Laravel deployment](https://laravel.com/docs/deployment).

## Проверки разработки

```bash
docker build -f tests/Dockerfile -t server-script-tests .
docker run --rm -v "$PWD:/work:ro" server-script-tests
# Статический анализ всех shell-файлов:
docker run --rm -v "$PWD:/work:ro" server-script-tests bash -c \
  'export LC_ALL=C.UTF-8; shellcheck -x *.sh lib/*.sh tests/*.sh'
```

Проверено в контейнерах **arm64**: Ubuntu 22.04 — PHP 8.3 со всеми расширениями через PPA и зависимости стека;
Ubuntu 24.04 — интеграционные тесты; Ubuntu 26.04 — полный набор зависимостей
с PHP 8.5 (8.3 отсутствует в стандартных индексах). Это не проверка amd64/VM.

Тесты в одноразовой Ubuntu 24.04 проверяют безопасное чтение/сохранение конфига,
недоступную версию/модуль PHP, повторное создание Git-ключа, права Git и ACL в обе
стороны, PostgreSQL на нестандартном порту с паролем со спецсимволами и повторным
созданием БД, генерацию и повторное применение Nginx-конфига через настоящий
`nginx -t`. В интеграционном тесте подменены systemctl, apt-get и Certbot;
он не проверяет реальный SSH-вход, GitHub/Bitbucket, UFW или выпуск сертификата.
Полный запуск на чистой VM со systemd остаётся обязательной проверкой перед
использованием на действующем production-сервере.
